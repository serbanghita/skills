# Copilot CLI logins survive VM recreation

Yes: the login of the standalone `copilot` binary can be saved and brought back on a recreated VM or pod without a new interactive login, and GitHub documents the mechanism that makes it possible. The credential is a plain bearer token with no machine binding found in any source, and the CLI accepts it from an environment variable (`COPILOT_GITHUB_TOKEN`), from stdin (`copilot login --with-token`, since 1.0.81), from a plaintext `config.json` under `COPILOT_HOME` on a keyring-less Linux box, or from the `gh` CLI as a last fallback. The recommended design is to do the one interactive step once per developer, keep the resulting token in a per-developer secret, inject it as `COPILOT_GITHUB_TOKEN` at every boot, and put `COPILOT_HOME` on a persistent volume for session state only. The narrowest token for that job is a user-owned fine-grained PAT carrying only the "Copilot Requests" permission; the OAuth token from `copilot login` or `gh` also works and appears to be non-expiring, but its scopes are wider or unknown. GitHub's terms do not prohibit a headless, always-on, per-developer agent and its docs recommend environment-variable auth for containers and headless servers; the binding constraints are "one login, one person", organization policy on the CLI, and cost. Since June 1, 2026 the CLI is billed in token-metered AI credits, so an always-on loop is a real, usage-proportional expense that needs a budget. A container test run after the desk research (CLI 1.0.100, two keyring-less Linux containers, described in its own section below) confirmed the three restore routes that matter: the environment variable, `copilot login --with-token`, and a restored `config.json` on a recreated machine. What remains unproven is the interactive device-code login inside a container, the invalid-token behaviour, and the OAuth app's scopes.

A note on evidence: the docs pages were read through a fetch tool that returns fragments, so quoted strings below should be re-checked against the page before being reproduced as verbatim. The latest CLI release at the research date (2026-11-26) was 1.0.116. The sections up to the container test are the desk research as written; where the test settled or corrected a point, the text says "measured".

## On headless Linux the whole login is one plaintext file

By default the CLI stores the OAuth token in the operating system's credential store under the service name **`copilot-cli`**: Keychain Access on macOS, Credential Manager on Windows, and libsecret (GNOME Keyring, KWallet) on Linux ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). When no keyring is reachable, "for example, on a headless Linux server without `libsecret` installed", it asks `System keychain unavailable. Store token in plaintext config file? (y/N)` and, on yes, writes the token into **`~/.copilot/config.json`** ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli); [Troubleshooting](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/troubleshoot-copilot-cli-auth)). Declining cancels the sign-in and leaves no account state behind ([issue #5399](https://github.com/github/copilot-cli/issues/5399)). A documented `settings.json` key, **`storeTokenPlaintext`** (default `false`), allows plaintext storage "when no system keychain is available" ([Configuration directory reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)); the container test showed it is required for a non-interactive login to save anything, and did not test the interactive question.

`COPILOT_HOME` replaces the entire `~/.copilot` path, and the plaintext fallback follows it: the token "is saved in a plain text configuration file under `~/.copilot/` (or `COPILOT_HOME`)" ([CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)). It does not relocate a keyring entry. On the macOS research machine the keychain item is `svce="copilot-cli"`, `acct="https://github.com:<login>"`, while `config.json` holds only account names (`loggedInUsers`, `lastLoggedInUser`) and no token. The consequence for a pod is the opposite of the desktop case: with no D-Bus and no keyring, the credential lives inside `COPILOT_HOME`, so one directory carries the login.

The file's token field is undocumented. The only description is a bundle excerpt from October 2025 showing a `copilot_tokens` map keyed `<host>:<login>` beside `logged_in_users` ([issue #207](https://github.com/github/copilot-cli/issues/207)); account fields have since moved to camelCase and, from 1.0.93, more of the CLI runs in a native Rust runtime ([issue #5085](https://github.com/github/copilot-cli/issues/5085)). GitHub describes `config.json` as "automatically managed application state", not a contract ([Configuration directory reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)). On 1.0.100 the field is `authTokens` (measured, below), which confirms the rename.

A keyring on a headless box is the fragile path and should be avoided on purpose. The open issues are about keyrings that are installed but unusable over SSH (still reported on 1.0.105 and 1.0.114), a default keyring that `copilot login` does not create, and a 20-second startup stall on an unresponsive Secret Service ([issue #2165](https://github.com/github/copilot-cli/issues/2165); [issue #3429](https://github.com/github/copilot-cli/issues/3429)). A GNOME keyring is also password-encrypted and needs an unlock per boot, which defeats unattended restore. The plaintext prompt itself regressed in 1.0.15 and 1.0.16 and was reworked in 1.0.51, 1.0.106, 1.0.107 and 1.0.115 ([issue #2494](https://github.com/github/copilot-cli/issues/2494); [changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)), so an image that performs a login must pin a tested CLI version.

## The token is a long-lived bearer with no refresh step

`copilot login` yields a **`gho_` OAuth-app token** for the "GitHub Copilot CLI" app. The CLI also accepts `github_pat_` fine-grained PATs with the "Copilot Requests" account permission, `ghu_` GitHub App user tokens via environment variable, and OAuth tokens from the `gh` app; classic `ghp_` PATs are rejected ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli); [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)). `ghs_` installation tokens work only in organization-billed setups with no user attached, so they cannot carry a developer's own subscription ([Server-to-server tokens](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/server-to-server-tokens)).

No source states an expiry for the CLI's `gho_` token; the Copilot docs say only that lifetime "depend[s] on how the token was created" ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). The evidence that it is long-lived is indirect but consistent: GitHub documents eight-hour expiry and refresh tokens for GitHub App `ghu_` tokens and not for OAuth-app tokens, and the research machine's keychain item was last written on 2026-04-23 and still authenticated seven months later. What ends such a token is documented: **one year without use**, revocation of the app authorization by the user or the app owner, a leak into a public repository, or exceeding **ten tokens per user, application and scope combination**, at which point an older token is revoked ([Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)). `/logout` removes the local copy and does not revoke the token on GitHub ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)).

Two of those rules shape a VM fleet. Each interactive `copilot login` mints a new token, so a developer who re-logs in on every rebuild will eventually push the oldest token over the ten-token limit; restoring one saved token consumes none of that budget. And an always-on agent never approaches the one-year inactivity clock. The short-lived "session token" mentioned in the changelog is most likely the Copilot API token re-derived at run time from the stored credential, and is not what needs backing up.

A fine-grained PAT is the contrasting choice: lifetime is **1 to 366 days or no expiry**, default 30 days, with infinite lifetimes subject to enterprise policy, and no browserless way to create or renew one was found ([Managing personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). It must be owned by the personal account, not an organization, and requests made with it "count towards the user's premium request allowance" ([Managing personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)).

## Four ways to bring the login back, one of them a documented contract

The CLI resolves credentials in a fixed order: `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, the stored OAuth token, then `gh auth token`, and "an environment variable silently overrides a stored OAuth token" ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). Every restore route is a way of feeding one of those five slots.

| Route | What survives the rebuild | Documented? | Main weakness |
|---|---|---|---|
| `COPILOT_GITHUB_TOKEN` from a secret | Nothing on the VM; the token lives in the secret store | Yes, "ideal for CI/CD pipelines, containers, or headless servers" | Rotation needs a process restart; a stale value masks a valid stored login |
| `copilot login --with-token` at boot (1.0.81+) | The token in the secret store, re-written into the CLI's own store each boot | Flag is documented; measured on 1.0.100 | Saves nothing and exits 1 unless `storeTokenPlaintext` is set first; adds a boot step for no gain over the env var |
| Persistent volume over `COPILOT_HOME` | Plaintext `config.json` plus sessions, settings, plugins | Location is documented; file shape is not | Token at rest in the volume and its snapshots; depends on an undocumented format |
| `gh` credential (mounted hosts file or `gh auth token`) | gh's plaintext token file, or its output exported as an env var | Fallback and token type are documented | `gh` tokens carry repository-wide scopes; lowest precedence when used as a fallback |

The environment variable is the only route that is both fully documented and independent of any file format. `COPILOT_GITHUB_TOKEN` exists precisely so Copilot can have a credential different from the `GH_TOKEN`/`GITHUB_TOKEN` other tools read, and its value is redacted from CLI output by default ([Automating with Actions](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/automate-with-actions); [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)). GitHub's own SDK Compose example mounts a volume only at `~/.copilot/session-state` and authenticates by environment variable, which is the same split ([Copilot SDK backend services](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/backend-services)).

The persistent-volume route is the simplest to operate and the least proven. Nothing in the old storage code is machine-specific, and a DDEV add-on reports that copying `~/.copilot` into a container "used to succeed on headless Linux" before it switched to exporting a token ([issue #207](https://github.com/github/copilot-cli/issues/207); [ddev-assistant-copilot](https://addons.ddev.com/addons/e0ipso/ddev-assistant-copilot)). The container test below supplied the first-hand check: a `config.json` written in one Linux container authenticated in a second, freshly created one.

The `gh` route matters because it offers a documented way to *obtain* an OAuth token as a string: a device-flow `gh auth login` followed by `gh auth token`. On Linux without a keyring `gh` writes its token to a plain text file, and `--insecure-storage` forces that ([gh auth login manual](https://cli.github.com/manual/gh_auth_login)). The Copilot CLI has no equivalent: there is no `copilot auth status` and no token-printing command as of 1.0.116, and an open request asks for one ([issue #5358](https://github.com/github/copilot-cli/issues/5358)).

## Recommended design: inject the token, persist only the state

Keep the credential in a per-developer secret (Kubernetes Secret, Vault, or the cloud's equivalent), export it as `COPILOT_GITHUB_TOKEN` when the agent process starts, and mount a persistent volume at `COPILOT_HOME` so sessions, settings and `--resume` survive. The VM then holds no login of its own, and recreating it is a non-event for authentication.

For the token itself there are two sound choices, and the trade is scope against ceremony. A **fine-grained PAT with only "Copilot Requests"** has no repository permissions, so a leak costs the developer's AI credits up to their budget and nothing else; it costs a browser visit to create and another at each expiry, unless a no-expiry token is allowed. An **OAuth `gho_` token** matches the "one interactive OAuth login" premise and has no fixed expiry, but the Copilot CLI app's scopes are known only from an unverified community comment (`read:user, read:org, repo, gist`), and a `gh` token is repository-wide by design, so either must be treated as a far broader secret. The PAT is the better default for a machine a company operates; the OAuth token is the better fit where a developer runs their own box and wants zero renewals. A company that wants short-lived per-user credentials has a third, heavier option: a GitHub App issuing refreshable `ghu_` tokens, the shape the SDK docs recommend with "set a token provider on each session instead of storing one long-lived token" ([Copilot SDK authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate)).

Several operating rules follow from documented behaviour. Rotation must update the secret and restart the process, because an environment token keeps precedence over a saved login and cannot change inside a running process ([Troubleshooting](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/troubleshoot-copilot-cli-auth)). Use `COPILOT_GITHUB_TOKEN` and never `GH_TOKEN` for this, since the latter also redirects `gh` and git tooling. Leave `gh` unauthenticated in the image and keep the volume free of a stored login, so a bad secret produces a documented error instead of a quiet fall-through; an earlier local measurement on 1.0.80 saw an invalid `COPILOT_GITHUB_TOKEN` fall through to `gh`, and the docs neither confirm nor refute that for current versions. Pin the CLI version and disable self-update, because the auth surface changed in 1.0.82, 1.0.99, 1.0.107, 1.0.110 and 1.0.115 alone ([changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). The agent also needs a second credential for git pushes and pull requests, since a Copilot-only PAT reaches no repository, and organization PAT and SSO policy clearly apply to that one.

Health checking is the weak spot. There is no documented entitlement probe that avoids spending a request; `/user` is interactive, and the undocumented `copilot_internal/user` endpoint changed shape in August 2026 in a way that broke the CLI itself ([issue #4627](https://github.com/github/copilot-cli/issues/4627)). The practical check is the first real run's error text: "No authentication information found", "Authentication failed", or "Access denied by policy settings" ([Troubleshooting](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/troubleshoot-copilot-cli-auth)). Long-running processes are in better shape than they were: a maintainer states that since 1.0.99 a session re-reads the stored credential after a 401, though the issue remains open ([issue #4929](https://github.com/github/copilot-cli/issues/4929)).

The fallback design, device login once with the whole `COPILOT_HOME` on a volume, is acceptable for a single developer's own VM; the container test showed the file restores cleanly on 1.0.100. Its costs are a plaintext token in every snapshot and backup of the volume and a dependency on a file format that has already been renamed once.

## Terms are silent on headless use; policy and credits are the real limits

### One login, one person

No GitHub term consulted prohibits running the CLI headless, unattended, on several machines, or on a company-operated VM. The applicable text is general: "Your login may only be used by one person", "You may not share API tokens to exceed GitHub's rate limitations", and the Acceptable Use Policies' bans on "automated excessive bulk activity", undue server burden and resale ([GitHub Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service); [Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)). A per-developer VM holding only that developer's token fits the one-person rule; a shared VM or a pooled token does not. That reading is an inference from the text, and the terms do not say whether a company operating the VM on the developer's behalf counts as the developer's own use. The product documentation points the same way without being a licence grant: environment-variable auth is recommended for containers and headless servers, and the SDK describes a backend passing "individual user tokens" per session ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli); [Copilot SDK backend services](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/backend-services)).

Enforcement risk attaches to behaviour, not to the hosting. GitHub publishes no rate-limit thresholds and names "frequent or automated requests" as a trigger ([Rate limits for GitHub Copilot](https://docs.github.com/en/copilot/concepts/rate-limits)). The suspension warnings in circulation come from unofficial proxy projects that expose Copilot's backend as a generic API, a different case from the official binary with a documented token type; no source reports enforcement against the official CLI run headless. Microsoft's Product Terms, which govern seats bought through Microsoft, were not consulted.

### Organization controls

For a seat assigned by an organization, the Copilot CLI client policy decides whether the CLI works at all; an enterprise "Disabled everywhere" overrides organizations, and a blocked user sees "Access denied by policy settings" ([Administering Copilot CLI for your enterprise](https://docs.github.com/en/copilot/how-tos/copilot-cli/administer-copilot-cli-for-your-enterprise)). Organization PAT policy (approval by default, a 366-day default maximum lifetime) is framed as gating access to organization-owned resources ([Setting a PAT policy](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)). Because the Copilot PAT's resource owner is the user, those policies plausibly do not reach it, but no page says so, and Enterprise Managed Users are an open question. Audit logging is documented only for policy changes, not for CLI sessions or token use.

### An always-on agent pays by the token

Since **June 1, 2026** all plans bill on GitHub AI Credits ([Updates to GitHub Copilot billing and plans](https://github.blog/changelog/2026-06-01-updates-to-github-copilot-billing-and-plans/)). One credit is **$0.01**, cost follows model and tokens, and credits reset monthly without carry-over; the CLI is a billed surface and agentic features make several model calls per task ([Usage-based billing for individuals](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals)).

| Plan | Price per month | Included credits per month |
|---|---|---|
| Pro | $10 | 1,500 (1,000 base + 500 flex) |
| Pro+ | $39 | 7,000 (3,900 + 3,100) |
| Max | $100 | 20,000 (10,000 + 10,000) |
| Business | $19 per seat | 1,900 per user, pooled |
| Enterprise | $39 per seat | 3,900 per user, pooled |

Sources: [Usage-based billing for individuals](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals); [Plans for GitHub Copilot](https://docs.github.com/en/copilot/get-started/plans).

This inverts the old economics. Under legacy premium-request billing, which survives only for annual Pro and Pro+ subscribers until their term ends, each CLI prompt cost one request and autonomous tool calls were free ([Requests in GitHub Copilot](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)). Under credits, every model call an idle-looping agent makes is metered. Two consequences deserve design attention: a user-level budget and session limits are the control for an unattended agent, and because Business and Enterprise credits are pooled at the billing entity, one developer's runaway VM draws down the organization's pool ([Usage-based billing for organizations and enterprises](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-organizations-and-enterprises)). The per-credit overage price was not read.

## Supported alternatives trade persistence for constraints

**Copilot cloud agent** removes the stored login from the design entirely, at the price of shape: sessions run at most 59 minutes, change only the one repository named at the start, and consume AI credits plus Actions compute ([About Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)). It replaces the VM only when the work is pull-request-sized.

**Remote control** (`copilot --remote`, generally available since May 18, 2026) lets the developer steer a session from GitHub.com or mobile, but it does not solve persistence: the session "must be actively running in a terminal", it does not work with `--prompt`, and organization seats need the "Store local sessions in the Cloud" policy set to "View and control" ([About remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)). It is a front end for the always-on VM, not a substitute for its login.

**The Copilot SDK headless server** (`copilot --headless --port 4321`) is the documented way to run the CLI as a service, with a service token, per-user tokens per session, or BYOK. It has no built-in auth between SDK and CLI and no idle timeout by default ([Copilot SDK backend services](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/backend-services)). Two further routes leave the developer's subscription behind: GitHub App installation tokens, which expire hourly, rotate by machine and bill the organization ([Server-to-server tokens](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/server-to-server-tokens)), and BYOK provider variables, which need no GitHub auth and bill the model provider while losing `/delegate` and the GitHub MCP server ([Authenticating Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). Neither is "bring your own Copilot".

## Container test: the login moved to two Linux containers

The test ran on 2026-11-26 with CLI 1.0.100, the version on the research machine, installed from npm into a `node:22-slim` image (Linux arm64, no keyring tools, non-root user). Two containers were started from it. The credential was the `gho_` token that `copilot login` had stored in the macOS keychain months earlier, read with `security find-generic-password -s copilot-cli -w`. Each run was `copilot -p` with a prompt asking for the single word `PONG`, with no tools available. One account and one version were tested.

| # | Container | What it was given | Result |
|---|---|---|---|
| 1 | first | `config.json` and `settings.json` copied from the Mac, no token | Failed: "Authentication token found but could not be validated", "Saved sign-in could not be read from credential storage" |
| 2 | first | the same files plus the token as `COPILOT_GITHUB_TOKEN` | `PONG` |
| 3 | second | empty home plus the token as `COPILOT_GITHUB_TOKEN` | `PONG` |
| 4 | second | `copilot login --with-token`, token piped on stdin, default settings | "Login succeeded, but the token was not saved. Install a system keychain or rerun login and accept plaintext storage."; exit 1; next run "No authentication information found" |
| 5 | second | `"storeTokenPlaintext": true` in `settings.json`, then the same login | "Signed in successfully as <login>"; exit 0; next run, with no token variable, `PONG` |
| 6 | first, destroyed and recreated | only the `config.json` from the second container | `PONG` |

Five findings follow.

**A macOS `~/.copilot` carries no login.** The copied `config.json` names the account but holds no token, and the CLI reports the missing keychain entry as an unreadable credential store (row 1). Moving a login off a Mac means reading the token out of the keychain.

**A non-interactive login saves nothing by default.** With stdin a pipe there was no question to answer: the CLI validated the token, declined to store it and exited 1, leaving `config.json` at its 131-byte initial state (row 4). Setting `storeTokenPlaintext` first made the same command store the token (row 5). A boot script that pipes a token into `copilot login --with-token` and ignores the exit code leaves the machine logged out.

**The plaintext shape on 1.0.100 is an `authTokens` map.** After row 5, `config.json` (mode 600, 593 bytes) held `authTokens` with two entries, keyed `<host>:<login>` and `<host>:<login>:github`, each an object with a `token` field carrying the same `gho_` string, beside `loggedInUsers` (now with `"kind": "githubDotCom"`) and `lastLoggedInUser`.

**The file is the whole login and is not machine-bound.** The recreated container in row 6 had a different hostname, no `settings.json` and no token variable, and authenticated from the restored `config.json` alone. The token itself had been minted on macOS, so it crossed operating systems as well as machines.

**A missing trust store looks like an auth failure.** The first attempts at rows 2 and 3 failed with "Authentication token found but could not be validated" and "Failed to fetch PAT user login: network fetch failed: request failed: error sending request for url (https://api.github.com/copilot_internal/user)", although the token was valid and Node's own `fetch` reached api.github.com from the same container. `node:22-slim` ships no system CA bundle; installing `ca-certificates` fixed it. The CLI's native HTTP client evidently uses the system trust store, not Node's bundled one.

The test did not cover the interactive device-code login inside a container, the plaintext question with a terminal attached, an invalid token, the token's scopes, or two processes sharing one `COPILOT_HOME`. Both containers were removed afterwards because they held the token.

## Conclusion

The question turns out to be less about persistence than about which artefact to treat as the login. GitHub has quietly made the token, not the machine, the unit of identity: every supported credential is a string the CLI will take from the environment, and the CLI's own stores are conveniences layered over that. Designing around the string rather than around `~/.copilot` gets a recreated VM back online with nothing but documented behaviour, and the container test bore that out: the same string worked from the environment, from stdin and from a restored file.

The harder decisions sit outside authentication. Usage-based billing means an always-on agent needs a spending ceiling before it needs a restore procedure, and the absence of a status command means the first failure will be discovered by a failed run. Of the measurements still open, the two that pay for themselves are the invalid-token behaviour on the pinned version, since it decides whether a bad secret fails loudly, and the app's OAuth scopes, since they decide whether the PAT's narrowness is worth its renewals.
